# PingKit Agent Instructions

## Project Overview

`PingKit` is a Swift package whose library target is dependency-free,
implementing dual-stack ICMP ping and IPv4 traceroute directly on
unprivileged ICMP datagram sockets — there is no vendored C engine and no
root requirement. The public surface is a Swift 6 `actor` + `AsyncSequence`
API. Design rationale, platform pitfalls, and the milestone roadmap live in
`PLAN.md`.

The package contains three layers plus a demo:

- `Sources/PingKit/`: the library — `Pinger` and `Tracer` actors, ICMP
  encoding/parsing (`ICMP/`), socket wrappers (`Socket/`), resolver, and
  public models. This is the only product consumers link.
- `Sources/PingKitCLI/`: the `pingkit-cli` executable built on
  `swift-argument-parser`.
- `Tests/PingKitTests/` and `Tests/PingKitCLITests/`: unit, parsing, and
  loopback integration tests.
- `Examples/PingDemo/`: an Xcode demo app generated from `project.yml`
  (XcodeGen); it consumes the package as a local dependency.

---

## Tech Stack

- **Language / Build**: Swift 6.0+ with strict concurrency; Swift Package
  Manager is the package and build system. Deployment targets are macOS 13+
  and iOS 16+ (`Duration` and the concurrency runtime set the floor);
  Linux is continuously verified in CI.
- **Transport**: unprivileged ICMP datagram sockets — `SOCK_DGRAM` with
  `IPPROTO_ICMP` / `IPPROTO_ICMPV6`, read through `DispatchSourceRead` on a
  private queue. No raw sockets, no entitlement, no `sudo`.
- **Concurrency**: `actor` state machines whose output is an
  `AsyncThrowingStream`-backed `AsyncSequence`, with one timeout `Task` per
  in-flight probe.
- **Timing**: `MonotonicTimestamp` over `CLOCK_UPTIME_RAW` (Darwin) /
  `CLOCK_MONOTONIC` (Linux), preferring the kernel's
  `SCM_TIMESTAMP_MONOTONIC` receive timestamp when the platform delivers it.
- **Name Resolution**: `getaddrinfo` through `Resolver`, honoring the
  system's RFC 6724 ordering rather than re-sorting addresses in-process.
- **Documentation**: DocC catalog at `Sources/PingKit/PingKit.docc`.
- **Demo**: SwiftUI app generated by XcodeGen from
  `Examples/PingDemo/project.yml`.

### Dependencies

- The `PingKit` library target has **zero dependencies**. Keep it that way:
  `swift-argument-parser` is linked only into the `PingKitCLI` executable,
  and `swift-docc-plugin` is used only for documentation builds. Do not add
  a dependency to the library target.

## Architecture

### Current Approach

- Two public actors own one run each: `Pinger` (echo) and `Tracer` (IPv4
  traceroute). Each owns its socket, pending probes, statistics, and
  lifecycle state (`idle` / `running` / `stopped`), and exposes a
  `nonisolated`, single-consumer `AsyncSequence` (`PingResponses`,
  `TracerouteHops`) fed by an `AsyncThrowingStream` continuation.
- The protocol layer (`ICMP/`) is pure functions over bytes: header
  encoding, the RFC 1071 checksum, and parsing of echo replies and ICMP
  error messages. It performs no I/O and is directly unit-testable.
- The socket layer hides every platform difference behind the internal
  `PingSocket` protocol (`activate`, `send`, `setTimeToLive`, `close`).
  `ICMPv4Socket` and `ICMPv6Socket` are the only `@unchecked Sendable`
  types in the library; each serializes its descriptor and dispatch source
  on a private queue.
- `Pinger` and `Tracer` take a `socketFactory` and a `resolver` through
  their internal initializer. That seam is what tests inject mocks through
  — keep it, and do not let an actor reach for a concrete socket type.
- There is no logging framework, no dependency-injection container, and no
  reactive stack. Do not introduce one; user-facing output belongs to
  `PingKitCLI`.

### Primary Data Flows

Ping execution follows this path:

```text
host String -> Resolver.resolve (getaddrinfo) -> ResolvedEndpoint
  -> socketFactory -> ICMPv4Socket | ICMPv6Socket
  -> send loop: ICMP echo encode -> socket.send -> .sent (or .sendFailed)
  -> DispatchSourceRead -> SocketDatagram(bytes, receivedAt, source, hopLimit)
  -> AsyncStream -> receive loop: parse, match on identifier/sequence
  -> pending probe resolved, timeout task cancelled
  -> PingResponse yielded on PingResponses, statistics accumulated
```

Traceroute follows this path:

```text
Tracer run loop: ttl in 1...maxHops
  -> socket.setTimeToLive(ttl) -> one echo probe per query
  -> Time Exceeded | Echo Reply | timeout -> ProbeOutcome
  -> TracerouteHop yielded on TracerouteHops
```

Round-trip time is measured against monotonic timestamps only — the
kernel's arrival timestamp where the platform provides it, otherwise
`MonotonicTimestamp.now()` in the receive path. Never introduce wall-clock
(`Date`) timing into these paths, and keep every timestamp on the single
clock base documented in `MonotonicTimestamp` so kernel and userspace
values remain subtractable.

### Where New Code Belongs

- Wire format, checksums, and parsing go in `ICMP/` as pure functions with
  unit tests against synthetic packets.
- Kernel and platform differences go in `Socket/`, behind `PingSocket`.
  macOS delivering the full IPv4 header on `SOCK_DGRAM` receives, Linux
  rewriting the echo identifier, a missing timestamp option — these are
  socket-layer concerns and must not leak into an actor's state machine.
- Address-family policy and name resolution go in `Resolver/`.
- Run lifecycle, reply matching, and statistics go in `Pinger.swift` and
  `Traceroute/Tracer.swift`.
- Public value types go in the top-level library files
  (`PingConfiguration`, `PingResponse`, `PingError`, `PingStatistics`,
  `IPAddress`, `IPv4Endpoint`).
- Flags, formatting, and anything that prints go in `Sources/PingKitCLI/`.
- On-device exploration goes in `Examples/PingDemo/`; the library must not
  gain a dependency or an API solely to serve the demo.

## Repository Layout

- `Sources/PingKit/Pinger.swift`: echo run lifecycle, probe matching, and
  statistics; `PingResponses` is its single-consumer sequence façade.
- `Sources/PingKit/Traceroute/`: `Tracer` actor and the traceroute value
  types (`TracerouteConfiguration`, `TracerouteHop`, `TracerouteProbe`).
- `Sources/PingKit/ICMP/`: ICMPv4/ICMPv6 encoding and parsing, the IPv4
  header reader, and `ReceivedPacket`.
- `Sources/PingKit/Socket/`: `PingSocket` protocol, `SocketDatagram`, and
  the two concrete unprivileged-ICMP socket wrappers.
- `Sources/PingKit/Resolver/`: `getaddrinfo` wrapper and `ResolvedEndpoint`.
- `Sources/PingKit/PingKit.docc/`: DocC catalog for the public API.
- `Sources/PingKitCLI/PingKitCommand.swift`: `pingkit` command with `ping`
  (default) and `trace` subcommands.
- `Tests/PingKitTests/`: checksum, packet-parsing, ICMPv6, `Pinger`,
  `Tracer`, and loopback integration tests, plus `Fixtures.swift`.
- `Tests/PingKitCLITests/`: argument-parsing tests for the executable.
- `Examples/PingDemo/`: XcodeGen-generated SwiftUI demo for device testing.
- `.github/workflows/ci.yml`: macOS, iOS, and Linux CI lanes.
- `PLAN.md`: design document of record — routes, platform pitfalls,
  milestones, and test strategy.

## Change Boundaries

- Keep public API changes in `Sources/PingKit/` and preserve the documented
  lifecycle semantics: `responses` is single-consumer (a second subscription
  throws `PingError.sequenceAlreadyConsumed`); each sequence number yields
  either `.sent` followed by exactly one terminal event, or a single
  `.sendFailed` with no `.sent`; `.sendFailed` is non-fatal and counts
  toward `transmitted`; cancellation and `stop()` are idempotent and release
  the socket and background send task.
- `PLAN.md` is the design document of record. When shipping a feature or
  changing direction, update its milestone sections rather than letting the
  plan drift from the code.
- README and `PLAN.md` reference the current release version (e.g. the
  installation snippet's `from: "…"`); bump them together when tagging a
  release.
- Product and scheme names are load-bearing: the executable is
  `pingkit-cli` (not `pingkit`) to avoid a case-insensitive collision with
  the library target, and `PingKit-LibraryTests` is the shared scheme that
  lets iOS test builds exclude the executable target. Renaming either breaks
  builds or CI.
- Regenerate `Examples/PingDemo` project changes through `project.yml`, not
  by hand-editing the generated Xcode project.
- Do not edit generated build output, `.build/`, or Xcode DerivedData.

## Development Rules

- **Zero Library Dependencies**: adding a package to the `PingKit` target is
  an architectural change, not an implementation detail. Solve it with the
  standard library and the platform, or move the need into the CLI.
- **Strict Concurrency**: everything crossing an isolation boundary is
  `Sendable`. The two socket classes are the only `@unchecked Sendable`
  types; a new one needs its serialization argument written down in the
  code, not assumed.
- **Keep The Socket Seam**: new platform behavior belongs in a `PingSocket`
  implementation. If a change forces the actors to know which socket they
  hold, the abstraction — and the tests that depend on it — is what needs
  fixing.
- **The Library Does Not Print**: no `print`, no logging framework, no
  stderr writes from `Sources/PingKit/`. Diagnostics reach the caller as
  events and errors; formatting is the CLI's job.
- **Errors Carry Values**: keep `errno` and ICMP codes in `PingError` /
  `PingResponse` payloads rather than folding them into strings, so callers
  can branch on them.
- **No Private Leakage**: resolved addresses, hostnames, and reply contents
  belong to the caller. Do not add telemetry, persistence, or diagnostic
  files that capture them.
- **Document The Contract**: public API carries DocC comments, and any new
  `AsyncSequence` states its consumer, cancellation, and termination
  semantics — that contract is the part tests and callers depend on.
- **Platform Claims Stay Honest**: macOS 13+ / iOS 16+; Linux verified for
  IPv4 and IPv6 echo with traceroute best-effort; tvOS, watchOS, and
  visionOS are not promised. Do not widen these in docs ahead of CI.
- **Code Hygiene**:
  - Every file terminates with exactly one trailing newline, with no extra
    blank lines at EOF.
  - No trailing whitespace on any line, to prevent diff noise.
  - Run `git diff --check` before committing; it reports both of the above
    in the staged diff.

## Behavior Verification

Before implementing, changing, testing, or documenting a feature, establish
what the correct behavior is — in this order:

1. **System CLI first.** Run the platform's `ping`, `ping6`, and `traceroute`
   with the relevant flags and observe the real output, for example
   `ping -c 3 127.0.0.1`, `ping6 -c 3 ::1`, or
   `traceroute -n -q 1 -m 4 1.1.1.1`. The library must match the CLI's
   observable semantics, not an assumption about them.
2. **OS socket semantics second.** PingKit sits directly on the kernel's
   unprivileged ICMP datagram sockets, so the mechanism layer is the
   platform, not project source. Confirm behavior against man pages, a small
   probe program, or kernel source (xnu, Linux `net/ipv4/ping.c`) rather
   than reasoning from the Swift API alone. For example, macOS delivers the
   full IP header on IPv4 `SOCK_DGRAM` receives while ICMPv6 receives carry
   only the ICMPv6 message; Linux ping sockets rewrite the echo identifier
   to the socket's bound port, so reply matching cannot assume the sent
   identifier comes back.
3. **RFC third.** When a wire format or protocol behavior has a formal
   definition, check the RFC and reflect that definition in documentation and
   tests: RFC 792 (ICMPv4), RFC 4443 (ICMPv6), RFC 1071 (internet checksum),
   RFC 3542 (IPv6 ancillary data API), RFC 6724 (address selection honored
   via `getaddrinfo` ordering). For example, traceroute depends on Time
   Exceeded messages as defined by RFC 792 / RFC 4443, and the checksum
   tests pin the RFC 1071 algorithm with known vectors.

Encode the verified behavior in tests: integration tests exercise real
loopback pings against the CLI's observable behavior, and unit tests pin
packet encoding, parsing, and matching semantics derived from the OS or the
RFC. Do not treat a surprising observation as a bug — and do not "fix" it —
before confirming it is not defined behavior. Never write an inference as if
it were an observation.

## Testing And Validation

Use the smallest relevant check first, then the complete suite:

```sh
swift test                                   # macOS: includes loopback integration tests
xcodebuild -scheme PingKit -destination 'generic/platform=iOS' build CODE_SIGNING_ALLOWED=NO
xcodebuild -scheme PingKit-LibraryTests -destination 'platform=iOS Simulator,name=<device>' test
```

Test-suite conventions (from `PLAN.md` §7):

- Protocol-layer pure functions get direct unit tests against synthetic
  wire-format packets built by `Tests/PingKitTests/Fixtures.swift`, which
  mirror what the kernel delivers on an ICMP datagram socket (IPv4 header
  included on Darwin). Golden fixtures captured from real packets (e.g. via
  `tcpdump`) are planned in `PLAN.md` §7 but not yet present.
- The socket layer is mocked through the internal `PingSocket` protocol to
  drive the state machine with injected replies, timeouts, and error
  messages.
- Integration tests ping `127.0.0.1` and `::1` only. They probe for
  unprivileged ICMP socket capability first and **skip** when it is absent —
  a permission problem must surface as a skip, never as a spurious failure
  or a spurious pass. External hosts are manual-only, never in CI.
- Lifecycle tests cover task cancellation, early loop exit, explicit
  `stop()`, double-close, and second-consumer rejection.

CI (`.github/workflows/ci.yml`) runs `swift test` on macOS (where the runner
allows unprivileged ICMP), an iOS device build plus simulator tests via the
`PingKit-LibraryTests` scheme, and a Linux matrix (Swift 6.0 and 6.1) in a
privileged container that enables `net.ipv4.ping_group_range` so the
integration tests run there too. Keep changes green on all three platforms;
Linux differences (identifier rewriting, no `SO_TIMESTAMP_MONOTONIC`) are
expected and handled in the socket layer, not by skipping Linux.

Know what the mock does and does not cover. `MockPingSocket` implements
`PingSocket` and delivers replies through the same `receiveHandler` the
actor installed, so the socket-to-actor wiring is genuinely exercised. What
it does not cover is everything inside `ICMPv4Socket` and `ICMPv6Socket` —
syscalls, control-message parsing, kernel receive timestamps, IPv4 header
handling, dispatch-source lifecycle — and the timing: the mock replies
inline from `send`, while the real socket replies later from its own queue.
Those gaps are closed only by the loopback integration tests, which skip
when the environment lacks ICMP capability, and by `Examples/PingDemo` for
what only a device shows (local network permission, NAT64, backgrounding).
A change inside a concrete socket can therefore pass every test on a machine
where the integration tests skipped.

Before considering a task complete: it builds, the relevant tests run, the
behavior is verified manually where a test cannot reach (device, IPv6-only
network, permission prompts), and any decision worth keeping has landed in
the repository.

## Repository First

AI conversations, ad-hoc plans, and execution context are ephemeral. Anything
valuable for future development or maintenance — requirements, constraints,
design rationale, validation conclusions — must be persisted in the
repository itself: issues, pull requests, commits, project docs, or necessary
code comments. Future maintainers should be able to understand the project's
important context from the repository alone.

Prioritize recording **why a change was needed**, **what important decisions
were made**, and **how the change was verified** — optimizing for
traceability, reviewability, and maintainability. Do not log AI tool names,
model names, agent modes, or step-by-step execution traces; per-commit AI
attribution is not required.

### Lightweight Workflow

For non-trivial changes, prefer: **Issue → Branch → Pull Request → Squash
Merge**. Keep the process light; do not add documentation work for its own
sake.

- **Language**: commit messages in English, following the Conventional
  Commits rules below; issue and pull request prose in Chinese, consistent
  with existing history.
- **Issue**: state why the change is needed, the expected result, and any
  acceptance criteria. Short is fine for simple tasks; no template required.
- **Implementation**: read the related issue and `PLAN.md` first, establish
  the correct behavior per [Behavior Verification](#behavior-verification),
  stay within the task scope, and avoid unrelated refactors or file changes.
  Update tests and docs when behavior changes. When a significant design
  choice arises, record the final decision and its reason — not every
  attempt or reasoning step. Ask instead of assuming when the issue and the
  code disagree.
- **Pull Request**: keep it to three short parts — *Summary* (what changed,
  with `Closes #…` where appropriate), *Decision* (important decisions and
  why; omit if none), *Validation* (build, test, or manual verification
  results, including the platforms covered). Do not generate long
  implementation reports, file lists, or step logs, and do not restate what
  the code already shows. Evidence that must outlive the change belongs in
  the issue or PR body; a local path is not evidence.
- **Human Review**: the repository owner owns every merge. Before merging,
  confirm the change matches the task goal, contains no obvious unrelated
  changes, and has validation proportional to its risk — without
  mechanically producing checklists.
- **Merging**: run issue, pull request, and merge operations through the
  local `gh` CLI. Wait for CI to pass on all three platform lanes instead of
  merging with `--admin`. `gh pr merge --delete-branch` does not reliably
  delete the remote branch — confirm with
  `git ls-remote --heads origin <branch>`.

### Decision-Driven Documentation

Code explains *how*; documentation should capture what code cannot express:
why the current approach was chosen, why alternatives were rejected,
important limitations, and compatibility or architecture trade-offs. Record
only decisions that genuinely matter for future maintenance — skip obvious
implementation details.

When executing any task, prioritize in order: (1) correct change, (2) focused
scope, (3) sufficient validation, (4) important decisions persisted to the
repository — with as little extra process and prose as possible. The
repository history is the long-term memory; AI conversations are only a
temporary workspace.

## Git Commit Message Conventions

Follow Conventional Commits. Every commit message uses this structure:

```text
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### Subject Line

- Max 50 characters
- Imperative mood: `add`, not `added` or `adding`
- Lowercase after the colon
- No trailing period

### Type Prefixes

Use one of:

- `feat` (new capability, e.g. a new response event or CLI flag)
- `fix` (bug fixes, e.g. reply matching or statistics accounting)
- `docs` (README, `PLAN.md`, DocC, or `AGENTS.md` updates)
- `refactor` (code restructuring with no behavior change)
- `test` (unit, parsing, or integration test changes)
- `perf` (allocation, latency, or throughput optimizations)
- `chore` (dependencies, package or project configuration)
- `ci` (workflow and platform-lane changes)

Scopes follow the layer or product they touch, for example `icmp`, `socket`,
`resolver`, `tracer`, `cli`, `demo`. Append `!` for breaking changes:

```text
feat(api)!: replace PingResponse.sent with a probe event
```

### Body

- Include a body only when needed.
- Explain why, not what. The diff shows what changed.
- Do not record AI tool names, model names, agent execution details, or
  validation checklists; that context belongs in the issue, PR, or docs
  (see Repository First).
- Wrap body lines at 72 characters.
- Separate the body from the subject with a blank line.

### Footer

- Reference issues with `Closes #123`.
- Mark breaking changes with `BREAKING CHANGE: <description>`.
